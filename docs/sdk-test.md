# SDK 测试文档

本文是 SDK v0.1 / 协议 v1 的测试计划，以 [SDK API 设计](sdk-api.md) 为契约依据，细化其第 12 节的验收项。当前 SDK 仍为模板代码，下文的 crate 路径、测试入口和检查命令均面向该设计实现后的结构，不表示对应测试已经实现或通过。

三方集成测试只使用 0、1、3 对属性，验证功能与协议一致性，不进行 Claims 压力测试、容量测试或性能测试。调用方配置限制的行为由独立进程中的单元测试使用较小阈值验证，不要求把集成测试数据扩展到默认容量上限。

## 1. 测试范围与职责

| 验证对象 | 负责层 | 测试要求 |
|---|---|---|
| 属性盲签发、解盲、凭证持有证明、选择披露、应用化名与验真 | SDK | 覆盖正常流程、输入边界、篡改和跨上下文拼接 |
| Claims 键数量、键名长度和属性值长度 | SDK 与调用方配置 | SDK 无固定字段数硬上限；通过 core 共享静态 `ClaimsLimits` 和 `unsafe set_claims_limits` 设置本地策略 |
| 登录挑战的格式、时间关系与到期时间 | SDK | `Holder::present` 和 `Verifier::verify_proof` 都检查；`now` 由调用方传入，SDK 不读取系统时间 |
| 挑战是否存在、是否已消费，以及消费时是否仍有效 | 应用后端 | 在 SDK 验真成功后，原子消费完整挑战记录并再次检查有效期；与创建会话一起提交 |
| 凭证有效期，以及 `expires_at`、`role` 等业务属性的含义 | 业务层 | 首版没有内建凭证有效期；SDK 只证明已披露键值经过签署，不自动解释时间或权限策略 |
| 成员身份核验、核准属性来源、签发唯一性与重试幂等 | 签发服务 | 使用可信资料核准属性，通过台账和事务保证唯一性、幂等性 |
| 用户披露同意、可信 origin 来源、本地加密与 Cookie 配置 | 钱包或应用集成层 | SDK 校验传入上下文的一致性，集成测试验证上下文来源和安全存储行为 |

SDK 测试不应预期 `Database`、`Io`、`AlreadyIssued`、`Replay` 或 `Session` 等错误。首版不承诺撤销、组织密钥轮换迁移、保留身份的属性续签、自然人唯一性或阻止主动复制秘密，不为这些能力编写成功断言。

## 2. 测试组织与共同约定

| 测试层级 | 建议位置 | 内容 |
|---|---|---|
| core 单元与边界测试 | `sdk/core/` | 共享静态配置、值类型、属性集合、编码、规范哈希、按需参数派生、群元素及配置限制 |
| issuer 单元与边界测试 | `sdk/issuer/` | 组织密钥、申领证明校验、属性核准匹配、盲签发和私密备份 |
| holder 单元与边界测试 | `sdk/holder/` | pending、解盲验签、披露选择、证明生成和私密备份 |
| verifier 单元与边界测试 | `sdk/verifier/` | 挑战、客户端绑定、时间和组合证明验真 |
| 三方离线集成测试 | `sdk/verifier/tests/` | 通过 dev-dependencies 引入 issuer、holder，使用公开 API 完成三方流程 |
| 固定协议向量 | `sdk/verifier/tests/fixtures/v1/` | 纳入版本控制的规范 JSON、请求哈希、消息编码及正反例 |
| 服务层集成测试 | 对应签发服务、应用或钱包工程 | 数据库台账、并发消费、会话、时钟来源、披露交互及存储 |

每条用例保留稳定编号，并记录前置条件、输入或篡改点、调用入口、预期结果及所属层级。表格中包含多个变体的条目应拆成参数化子用例；优先匹配错误枚举，不依赖 `Display` 文案。

- 使用固定 Unix 秒和满足 `RngCore + CryptoRng` 的可复现测试随机源，不依赖真实等待、网络、数据库或被 Git 忽略的 references 目录。不同操作使用独立种子或连续推进随机源；验证随机化时不能每次重置为同一随机状态。生产随机源仍须满足安全要求。
- 默认夹具准备两个 issuer、两个不同秘密的 holder、两个应用 origin，以及带 `department`、`display_name`、`role` 的凭证；另建 0、1 对属性样本，3 对属性足以覆盖多个隐藏属性。
- 默认配置测试可以并行只读。使用 `unsafe set_claims_limits` 的测试必须在独立子进程初始化阶段设置配置，在任何其他 SDK 调用前完成，并在该进程内保持不变。不能只给设置函数加锁、在同一进程反复切换配置或与其他 SDK 读操作并发；测试全局变量不能引入数据竞争。
- 负例先确认原始夹具可成功，再逐项引入目标缺陷。需要到达密码学检查时，其余格式、绑定、披露和时间条件必须合法。
- 对公开 DTO 同时覆盖 JSON 输入和直接构造、解析后修改两条路径。角色方法必须重新校验当前输入，解析成功不代表凭证或证明可信。
- 多处同时非法时遵循 API 规定的检查顺序，例如 verifier 先比较完整挑战。为断言 `IssuerMismatch`、时间错误或 `InvalidPresentation`，不能先被 `ChallengeMismatch` 拦截。
- 角色错误中的 core 错误通过 `Error::Core(...)` 断言。API 未固定具体 core 变体的解析失败，只断言契约要求的错误类别和拒绝行为；属性资源超限允许 API 约定的 `InvalidClaims` 或 `InputTooLarge`。
- 下列 SDK 用例均为首版验收项；服务层用例单独验收。属性测试和模糊测试作为后续加固，不代替确定性用例。

## 3. 身份稳定性与隔离

subject 的稳定前提是相同 issuer、相同秘密 `x` 和相同规范化 origin；“同一个钱包程序”本身不能保证这个前提。subject 必须从成功验真的 `VerifiedProof` 读取，不能使用未经验证的请求字段充当结果。

| 编号 | 前置条件与操作 | 预期结果 |
|---|---|---|
| ID-01 | 同一凭证、同一 origin，在有效时间内使用不同 nonce 的挑战多次出示并验真 | subject 相同 |
| ID-02 | 同一凭证、同一 origin，分别不披露、部分披露、全部披露；挑战要求与选择相容 | 均验真成功，subject 不随披露选择或必需键集合变化 |
| ID-03 | 对同一个有效申领请求重复盲签发，推进随机源；分别用原 pending 解盲并出示 | 各签名均有效，subject 相同；不要求 SDK 返回同一份签发响应 |
| ID-04 | 内部夹具固定 issuer 和 `x`，为不同属性值及不同属性数量生成有效凭证 | subject 相同，issuer 指纹不随属性数量变化 |
| ID-05 | holder 导出后恢复，在同一 origin 出示 | subject 和完整属性保持不变 |
| ID-06 | 同一 issuer、相同属性，使用两个不同秘密的 holder 向同一 origin 出示 | subject 不同 |
| ID-07 | 内部夹具固定 `x`，分别改变规范化 origin 或 issuer；使用各自有效凭证和 verifier | subject 不同，不能跨 issuer 或应用使用证明 |
| ID-08 | 分别用 `HTTPS://FORUM.EXAMPLE.ORG:443/` 和 `https://forum.example.org` 配置同一应用；另测非默认端口 | 前两者规范化后 subject 相同；非默认端口产生不同 subject |
| ID-09 | 连续调用两次 `begin_enrollment` 并完成申领，不复位随机源 | 生成新的秘密和请求上下文，同一应用的 subject 改变 |

ID-04 和固定 `x` 的跨 issuer 用例通过内部测试辅助方法构造，不增加读取或指定 `x` 的生产公开接口。首版公开 API 不支持保留原身份更新属性；身份恢复通过导入既有 holder 备份完成。业务路径不构成新 origin；`Origin::parse` 本身必须拒绝非根路径。

## 4. 申领、盲签发与解盲

本组以 issuer、holder 单元测试为主，EN-01、EN-07 同时纳入三方集成测试。

| 编号 | 调用入口与操作 | 预期结果 |
|---|---|---|
| EN-01 | 初始化组织，执行 `begin_enrollment → issue_blind → finish → present → verify_proof`，分别使用 0、1、3 对合法属性 | 全流程成功；holder 保存完整属性，`VerifiedProof` 返回已验证 subject 与所选属性；领证后出示和验真仅使用钱包凭证与 issuer 公钥 |
| EN-02 | `issue_blind` 的核准集合与请求相比，分别改值、缺项、增项，含越权 `role=admin` | 返回 issuer 的 `ClaimsMismatch`，不签发、不自动删改属性 |
| EN-03 | 在合法申领请求中分别篡改承诺、开口知识证明或完整属性；属性变体同时调整核准集合以保持相等 | 在签发前拒绝；格式合法但证明不成立时为 `InvalidEnrollmentProof` |
| EN-04 | 把合法申领请求交给另一个 issuer；或修改请求的组织绑定 | 返回 `IssuerMismatch`；非法编码由 core 校验拒绝 |
| EN-05 | 对固定请求的 JSON 调整对象字段顺序、空白、等价转义；另对同一请求 ID 改动键或值 | 等价输入的规范 `request_hash` 相同；请求内容变化时哈希改变；哈希结果不代表申领证明有效 |
| EN-06 | `finish` 收到其他 issuer、其他 request ID、其他 request hash 或不同完整属性的响应，分别构造单一缺陷 | issuer 不符为 `IssuerMismatch`；其余请求上下文不符为 `EnrollmentMismatch` |
| EN-07 | 保持响应元数据和属性匹配 pending，只篡改签名，或替换为错误 issuer 私钥生成的签名 | `finish` 返回 `InvalidCredential`，不创建可用 holder |
| EN-08 | `finish` 先接收错误响应，再用同一个 pending 接收正确响应；另在恢复 pending 后重试 | 错误不销毁 pending，正确响应仍能完成申领；成功后由钱包负责持久化 holder 和清理 pending |
| EN-09 | `Issuer::generate` 输入空组织名、超过 128 字节、首尾空白或控制字符；另测合法边界 | 非法组织名被拒绝，合法组织名可使用；内部密钥测试确认私钥非零 |

## 5. 选择披露与组合证明

### 5.1. 正常披露与选择约束

| 编号 | 调用入口与操作 | 预期结果 |
|---|---|---|
| DS-01 | 无必需键时，`present` 分别选择空集、任意合法子集、全集 | 均验真成功，返回的键值恰为所选集合；`claim_count` 仍为完整属性数量 |
| DS-02 | `present` 选择凭证中不存在的键 | 返回 holder 的 `InvalidDisclosure` |
| DS-03 | `present` 的选择缺少一个或多个 `required_claims`，包括凭证根本不包含必需键的情形 | 返回 holder 的 `MissingRequiredClaims`，不自动增加披露项 |
| DS-04 | 为 verifier 构造格式合法但缺少必需披露键的输入，完整挑战与存储一致 | 返回 verifier 的 `MissingRequiredClaims` |
| DS-05 | 合法签署 `role=guest`，应用只在挑战中要求键 `role` | SDK 验真成功并返回 `guest`；是否允许登录由应用值策略决定 |
| DS-06 | 比较未披露键和已签署、已披露但值为空字符串的键 | 前者在验真结果中为 `None`，后者为 `Some("")`；不把未披露解释为不存在 |
| DS-07 | 同一 holder 连续使用不同披露子集，包含多个隐藏属性、首尾槽位和不连续槽位 | 每种合法组合均可验真，holder 完整属性不变；全部披露时 `x` 仍隐藏 |

### 5.2. 篡改与拼接对抗用例

以下用例由 verifier 测试拒绝行为，涉及底层证明构造时使用内部辅助方法或固定对抗向量。合法结构中的密码学不一致返回 `InvalidPresentation`；非法编码可以更早被 core 拒绝。每个攻击样本都应有对应的有效样本。

| 编号 | 篡改点 | 预期结果 |
|---|---|---|
| AT-01 | 保留证明，修改已披露属性的键或值；选用仍满足格式、排序和必需键条件的变体 | 不能作为原签名的有效属性通过验真 |
| AT-02 | 调换属性槽位，构造重复索引、重复键、越界索引、索引错序或可见键错序 | 全部拒绝；`index` 必须对应属性槽位 `i`，其签名消息索引为 `3 + i` |
| AT-03 | 小规模样本只修改 `claim_count`，例如把 3 改为 2 或 4；其余披露格式保持合法 | 拒绝错误消息布局或不匹配的证明结构，不需要构造真实的大规模凭证 |
| AT-04 | 在已有证明中增加未签署属性、移除非必需披露项，或增删披露项但复用原证明 | 拒绝；删除必需项另由 DS-04 覆盖 |
| AT-05 | 将凭证 A 的持有证明与凭证 B 的化名关系证明或不匹配的披露项拼接；包含属性完全相同但 `x` 不同、化名不同的两张凭证 | 拒绝关系不一致的跨凭证拼接；仅复制完全相同的披露项字节不构成可区分的攻击 |
| AT-06 | 构造 BBS+ 持有证明有效，但化名使用另一秘密的对抗样本 | 拒绝共享秘密关系不成立的证明；分别覆盖仅隐藏 `x` 和还隐藏多个属性 |
| AT-07 | 修改、遗漏或增加隐藏消息响应，或把某个隐藏属性的响应作为索引 0 的秘密响应 | 拒绝不完整或错位证明；响应数量必须与 `claim_count` 和披露数量相符 |
| AT-08 | 把化名替换为另一个有效非零群元素；另测零点、非子群点和无效点编码 | 合法点但关系不符时验真失败；非法点在结构或群元素校验阶段拒绝 |

## 6. 挑战、origin 与客户端绑定

| 编号 | 调用入口与操作 | 预期结果 |
|---|---|---|
| CH-01 | `create_challenge` 连续创建挑战 | 每次产生独立的 32 字节 nonce 和客户端秘密；秘密哈希及显式必需键被绑定，客户端秘密不包含在公开挑战中 |

| CH-03 | 输入挑战与保存挑战一致，但 issuer 或 origin 与 verifier 的固定配置不符 | 分别返回 `IssuerMismatch`、`OriginMismatch`；不从输入动态切换信任源 |
| CH-04 | `present` 输入其他 issuer 的挑战，或挑战 origin 与独立传入的 `trusted_origin` 不一致 | 分别返回 holder 的 `IssuerMismatch`、`OriginMismatch` |
| CH-05 | 合法 presentation 与原存储挑战匹配，改用另一合法客户端秘密；另测非法 Cookie 编码 | 前者返回 `ClientBindingMismatch`；后者在 `ClientBindingSecret::from_cookie_value` 处被拒绝 |
| CH-06 | 将证明移用至另一挑战，同时替换 presentation 内挑战与保存挑战，并提供新挑战对应的客户端秘密 | 前置格式、必需键和时间均合法时，仍因完整挑战未被原证明绑定而返回 `InvalidPresentation`；分别改变 nonce、有效时间、绑定哈希和相容的必需键集合 |
| CH-07 | 将合法 subject 仅作为字符串解析，另提交没有有效证明的 presentation | `Subject::parse` 可接受合法点编码，但 verifier 不因此建立身份，不能产生 `VerifiedProof` |

## 7. 登录挑战的时间边界

本节只验证 `LoginChallenge` 的时效。`Holder::present` 和 `Verifier::verify_proof` 应分别覆盖下表的校验用例。验证方输入必须与存储挑战一致；用例仅检查时间时，不能因挑战不一致而提前失败。需要成功验真的样本应针对对应挑战重新生成有效证明。

`now`、`issued_at`、`expires_at` 均为 `u64` Unix 秒。生产由调用方传入钱包设备时间或后端服务器时间；测试使用固定时间，推进参数即可，不进行真实等待。

| 编号 | 条件或操作 | 预期结果 |
|---|---|---|
| TM-01 | `create_challenge(now=t)`，且 `t + 120` 不溢出 | `issued_at=t`、`expires_at=t+120`；创建接口固定 120 秒 TTL |
| TM-02 | 合法挑战，`now=expires_at-1` | 时间检查通过 |
| TM-03 | 合法挑战，`now=expires_at` 或 `expires_at+1` | 返回 `ChallengeExpired`；到期没有 30 秒宽限 |
| TM-04 | `issued_at=now+30` 和 `issued_at=now+31`，其他条件合法 | 前者时间检查通过，后者返回 `InvalidChallengeTime` |
| TM-05 | `expires_at=issued_at`、小于 `issued_at`，或 TTL 为 121 秒 | 返回 `InvalidChallengeTime`，不发生下溢 |
| TM-06 | 外部输入挑战的 TTL 分别为 1、119、120 秒，当前时间有效 | 时间检查通过；验证接受 `0 < TTL <= 120`，不代表创建接口支持自定义 TTL |
| TM-07 | 创建时间为 `u64::MAX-120` 及再加 1；另测接近整数上下界的时间校验 | 前者可创建，后者以 `InvalidChallengeTime` 拒绝；所有时间运算不溢出、不 panic |
| TM-08 | 钱包出示时尚未到期，后端验真时已到期 | 钱包可生成证明，但后端返回 `ChallengeExpired`；后端按自己传入的当前时间决定结果 |

验真结束到挑战原子消费之间可能到期，应用必须重新读取当前时间，并在消费条件中要求 `expires_at > commit_now`。这属于服务层用例 SV-03，不由无状态 SDK 保证。业务属性中即使存在字符串 `expires_at`，也不参与上述挑战时间计算。

## 8. 值类型、属性与严格编解码

### 8.1. 共享静态配置

本组的配置值与基础边界放在 core 单元测试，跨角色共享检查使用 verifier 现有 dev-dependencies 构建的独立测试程序，core 不反向依赖角色包。配置接口定义见 API 第 7.2 节。不同配置场景各自启动进程，不通过测试非法并发调用来验证 `unsafe` 契约。

| 编号 | 配置与操作 | 预期结果 |
|---|---|---|
| CF-01 | 不调用设置函数，读取 `DEFAULT_CLAIMS_LIMITS` 和 `claims_limits()` | 默认为 128 个键、64 字节键名、1024 字节值；读取返回值副本 |
| CF-02 | 初始化设置 `max_keys=4`、`max_key_bytes=8`、`max_value_bytes=16`，再从三个角色的重导出入口读取并执行适用校验 | 角色共享同一 core 静态配置；值类型、wire、角色入口和备份操作按当前配置校验，不各自保留硬编码上限 |
| CF-03 | 独立进程设置 `256 / 128 / 2048`，单元测试分别构造 33 个短属性、65 字节合法键名和 1025 字节值 | 构造与编码校验通过，证明旧阈值不再是硬上限；只验证属性和编码，不要求签发、生成证明或压力测试 |
| CF-04 | 初始化阶段先设置合法配置，再尝试设置 `max_key_bytes=0`，之后读取配置 | 返回 `InvalidClaimsLimits`，保留上次合法配置；失败不会部分更新字段 |
| CF-05 | 分别在独立进程设置 `max_keys=0` 和 `max_value_bytes=0`；另在不构造数据的进程设置 `max_keys=usize::MAX` | 前者只接受空集合；第二种配置只接受空字符串值；极大配置值可保存，不预分配内存或参数组 |
| CF-06 | 两个独立进程使用不同但均允许同一小规模样本的配置，固定其输入和随机种子 | 合法输入的规范编码、请求哈希、issuer 指纹和 subject 一致；本地配置不进入消息或密码学转录 |

CF-02 的字段边界使用下面的小配置样本，采用 `a`、`b`、`c` 等短键和短值，避免默认夹具中的长键提前超限；其中 `Presentation::claim_count` 和必需键、选择键的数量也须按当前配置校验。CF-03 只是廉价回归用例，不把 33 作为新的上限或集成测试规模。

### 8.2. 属性语义与资源边界

| 编号 | 输入或操作 | 预期结果 |
|---|---|---|
| CO-01 | `Claims::new`、`ClaimKeys::new` 以不同插入顺序构造同一集合 | 按键 ASCII 字节序排序，迭代、查找、长度和空集行为一致 |
| CO-02 | 重复业务键、重复选择键；非法键含大写字母、空格、非 ASCII、数字开头或通配符 | 返回 `InvalidClaims`；重复项不能被收集成映射时静默覆盖 |
| CO-03 | 属性值使用数字、布尔、数组、对象或 `null`；另测合法空字符串 | 非字符串被拒绝，空字符串被保留 |
| CO-04 | 值含首尾空白、多字节 Unicode、不同 Unicode 规范化形式；等价 JSON 转义与字面字符 | 不 trim、不进行 Unicode 归一化；不同原始字符串保留差异，解码后相同字符串具有相同规范编码 |
| CO-05 | 组织相同但公钥不同，或公钥相同但组织不同；属性数量与披露选择变化 | 前两者的 issuer 指纹不同；仅改变属性数量或披露选择不改变指纹 |
| CO-06 | 解析 issuer/request/hash/nonce 的错误长度、大写 hex、非法字符；解析错误群元素 | 拒绝非规范编码、无效点、非子群点及要求非零处的零点 |
| CO-07 | `Origin::parse` 输入 HTTPS、HTTP loopback、非 loopback HTTP、userinfo、非根路径、查询或 fragment | 仅接受规定 origin；规范化 scheme、host、默认端口并输出 ASCII origin，其余拒绝 |
| CO-08 | 按下表分别构造各项资源边界，覆盖值类型、wire 和适用的角色入口 | 合法边界通过；超限被拒绝，不因字节数、字符数或编码形式混淆而绕过限制 |

下面使用 CF-02 的 `4 / 8 / 16` 小配置覆盖边界，不构造默认容量或大规模属性。所有长度均按解码后的 UTF-8 字节数计算，单独引入一项超限，其余条件保持合法。

| 边界 | 合法样本 | 非法样本 |
|---|---|---|
| 属性数及选择键数量 | 0、1、4 | 5 |
| 键的 UTF-8 字节数 | 1、8，且符合 `[a-z][a-z0-9_.-]*` | 0、9 或语法非法 |
| 单个值的 UTF-8 字节数 | 0、16，含多字节字符样本 | 17 |

数量和长度校验分别覆盖 `wire::from_json`、`wire::to_json` 和适用的角色秘密导入导出。使用 JSON 转义后变大的短字符串验证长度按解码后的字节计算；不再断言固定属性总字节数或整体消息字节数上限。HTTP、文件和备份读取总量属于调用方入口策略。

### 8.3. JSON、证明结构及可变 DTO

| 编号 | 调用入口与操作 | 预期结果 |
|---|---|---|
| WI-01 | 对五种公共消息执行解析、规范输出和再次解析 | 数据一致，输出为固定字段顺序的紧凑 v1 JSON；`Claims`、`ClaimKeys`、`DisclosedClaim` 不是额外顶层消息 |
| WI-02 | 调整输入 JSON 对象字段顺序、合法空白或等价转义 | 规范输出一致；完整请求的规范哈希一致 |
| WI-03 | 缺失集合字段、用 `null` 替代集合；未知字段、重复结构字段或重复业务键 | 拒绝；空集合须显式为 `{}` 或 `[]`，覆盖顶层和 `DisclosedClaim` 内嵌结构 |
| WI-04 | `ClaimKeys` 或 `disclosed_claims` 的数组重复、错序；属性索引为负数、非整数、超出 `u64` 或满足 `index >= claim_count`；计数转为平台类型或 `3 + n` 溢出 | 拒绝，不截断、不回绕、不静默排序；用短编码和伪造数值验证，无需分配对应数量的元素 |
| WI-05 | 非支持版本、无效 UTF-8、截断 JSON、额外尾随非空白字节、非规范 hex 或不合法证明结构 | 拒绝；版本错误对应 `UnsupportedVersion`，其他按 API 的 core 错误类别断言 |
| WI-06 | 用短输入伪造超过当前配置或与实际属性、披露数量不匹配的证明容器长度，另测截断数据 | 按配置和结构拒绝，不依据伪造长度预分配，不接受部分响应证明；无需真实大输入 |
| WI-07 | 原始 JSON 的 origin 使用大小写、默认端口等非规范形式 | wire 解析拒绝；仅业务配置的 `Origin::parse` 可以规范化输入 |
| WI-08 | 绕过 wire，直接构造非法 DTO；或解析后修改字段，使版本、组织绑定、属性、披露项、时间或证明违反相应格式或角色上下文契约 | 对应角色入口仍拒绝非法输入；不能依赖 DTO 来源建立信任 |
| WI-09 | 修改 `IssuerPublic` 或 `EnrollmentRequest` 的内容后再次调用 `issuer_id()` 或 `request_hash()` | 按当前内容重新计算或返回错误，不返回旧缓存值；既有角色对象使用自己的已验证上下文，不被外部 DTO 修改切换信任源 |

## 9. 秘密备份、恢复与日志

| 编号 | 调用入口与操作 | 预期结果 |
|---|---|---|
| BK-01 | issuer 导出并使用正确 `expected_issuer` 导入 | 公钥、组织和 issuer 指纹保持不变，恢复后可正常签发 |
| BK-02 | pending 导出恢复，再完成原请求；分别篡改请求、请求哈希、秘密或盲因子 | 正常恢复成功；不一致的请求、开口关系或证明被拒绝，仍须在 `finish` 最终验签 |
| BK-03 | holder 在只披露部分属性后导出恢复 | 完整属性和有效凭证被保留，原隐藏属性之后仍能选择披露，原应用 subject 不变 |
| BK-04 | holder 备份只改秘密或签名；或改动仍合法的属性值并保持其他上下文一致 | `import_secret` 返回 `InvalidCredential`；零秘密及非法属性也必须拒绝 |
| BK-05 | 各角色秘密导入使用错误版本、错误预期信任源、公私钥不一致或超过当前配置的属性数量、键名及值长度 | 拒绝导入，不悄悄切换组织、公钥或创建可用运行时对象 |
| BK-06 | 秘密对象的类型能力，以及公共消息 `Debug` 和错误 `Display`/`source` | 通过编译失败用例确认秘密对象不实现 `Debug`、`Clone` 或通用 Serde 序列化；公共消息日志隐藏属性值和大体积密码学字段，错误链不泄露原始秘密或敏感中间值 |

秘密导出是未加密本地备份，不应断言它对持有备份字节的人隐藏秘密；加密存储由集成层验证。对清理逻辑只验证可观察且受 SDK 控制的缓冲区行为，不通过读取已释放内存测试擦除，也不承诺消除操作系统或第三方库中的全部副本。

## 10. 随机化、隐私与固定协议向量

| 编号 | 检查内容 | 预期结果 |
|---|---|---|
| PV-01 | 同一 holder、同一挑战、相同披露集合，推进随机源连续生成证明 | 证明密码学字段发生随机化，均可验真且 subject 相同；不以挑战改变造成的 JSON 差异代替随机化断言 |
| PV-02 | 检查 presentation 的结构及序列化输出，使用与公开字段不重合的隐藏属性标记 | 不额外输出隐藏键值、属性哈希、完整键清单、完整属性摘要、申领标识或原始凭证签名；允许公开 `claim_count` 和披露槽位 |
| PV-03 | 使用固定、经审阅的 v1 参数与小规模消息向量，在允许样本的不同配置下分别重验 | 核对固定用途基点、按需派生的消息基点前缀、issuer 指纹、组织消息、`Fr(n)` 及键值消息；已有基点不随配置或请求数量变化，空属性仍有前三条消息 |
| PV-04 | 从版本控制的 fixtures 重验规范 JSON、请求哈希、有效凭证、不同披露组合及无效证明 | 输出与固定向量一致，有效样本通过，无效样本按目标原因拒绝；失败时不能通过自动重写期望值消除差异 |
| PV-05 | 跨申领证明和登录证明用途复用数据，或改变应受转录绑定的上下文 | 不接受跨用途或上下文复用，覆盖 v1 各域分离标签 |

固定向量应记录版本、输入来源、测试随机种子、预期结果和生成方式，只使用合成秘密。向量核对独立计算的消息编码和哈希，避免仅靠同一实现的生成与解析往返掩盖共有错误。v1 已扩展属性签名，参考实现没有定义的字段不能直接当作互通向量。

上述测试验证协议输出和行为，不把“JSON 中找不到明文”当成不可关联性的完整证明。属性数量、槽位及已披露属性可能提供关联线索，披露唯一姓名或成员编号本身会影响隐私。

## 11. SDK 无状态边界与服务层配套测试

| 编号 | 测试层级与操作 | 预期结果 |
|---|---|---|
| SV-01 | SDK：在同一有效时间内，用同一客户端秘密和存储挑战重复调用 `verify_proof` | 可以重复验真成功；SDK 不因先前调用产生 `Replay`，也不自动消费挑战 |
| SV-02 | 应用：多个请求先完成 SDK 验真，再竞争消费同一完整挑战记录 | 只有一个请求能消费并创建会话；消费与会话创建同事务提交，失败时不设置会话 Cookie |
| SV-03 | 应用：SDK 验真时未到期，执行原子消费时恰好到期；另测消费与会话创建失败回滚 | 要求 `expires_at > commit_now`，到期后拒绝创建会话；事务失败不遗留已登录状态 |
| SV-04 | 应用：找不到待处理挑战、挑战已消费，或记录只有 nonce 相同而其他内容不同 | 由应用拒绝；保存并比较完整挑战，不把请求中的副本直接当作可信存储记录 |
| SV-05 | 签发服务：同一已授权成员、同一完整请求和核准集合重试；另测同成员换请求、同请求换成员、同请求 ID 改属性及并发竞争 | 合法重试返回持久化的同一响应；冲突被台账拒绝，响应和签发记录原子持久化；SDK 本身不保证签发幂等 |
| SV-06 | 业务层：签署的 `expires_at` 已过期，或签署 `role=guest` 但应用只允许 `member` | 满足挑战和证明条件时 SDK 仍可验真成功；应用从 `VerifiedProof` 读取属性并按业务策略拒绝 |
| SV-07 | 钱包与应用集成：挑战要求更多属性、伪造来源 origin、错误 Cookie 来源及客户端时钟偏差 | 用户选择被显式尊重，可信 origin 不直接复制挑战，Cookie 秘密独立于 presentation，服务端使用自己的时钟；验真结果仅证明对应签名与上下文有效 |

## 12. 执行与验收

完成四个 crate 的实现后，在仓库根目录执行：

```sh
cargo test -p crypto-sso-core -p crypto-sso-issuer -p crypto-sso-holder -p crypto-sso-verifier
cargo fmt -p crypto-sso-core -p crypto-sso-issuer -p crypto-sso-holder -p crypto-sso-verifier -- --check
cargo clippy -p crypto-sso-core -p crypto-sso-issuer -p crypto-sso-holder -p crypto-sso-verifier --all-targets -- -D warnings
cargo tree -p crypto-sso-issuer -e normal
cargo tree -p crypto-sso-holder -e normal
cargo tree -p crypto-sso-verifier -e normal
```

验收时记录每个用例编号对应的测试函数、运行结果和未完成原因。SDK 内部的正常依赖由三个角色指向 core，不出现角色间依赖边；三方测试经 verifier 的 dev-dependencies 引入另外两个角色。确认 fixtures 随 verifier 包发布，不依赖 workspace 外部文件。SDK 检查不以整个 Tauri workspace 构建代替。自定义全局配置用例由隔离测试进程执行，不靠修改测试线程数规避初始化约束。

后续加固可在小规模输入下使用属性测试生成不同集合顺序、披露子集和单点篡改，使用受限长度的模糊输入覆盖 JSON、证明与秘密备份解析，重点检查 panic、越界、整数溢出和不受限分配。本计划不包含大规模 Claims 压力测试或性能验收。加固测试失败时保存可复现输入，并补充确定性回归用例。
